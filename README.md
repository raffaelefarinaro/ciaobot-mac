# Ciaobot for Mac

A client-only macOS 13+ app for a separately installed Ciaobot server. It does not install, manage, restart, or replace the server or its workspace. The connection screen shows the original Ciaobot face beside its title. The image is decorative and hidden from VoiceOver; it ships in the client's SwiftPM resources and the generated `.app` bundle, never as a runtime read from the server checkout.

The generated `.app` also carries the PWA artwork as its native icon (`AppIcon.icns`, referenced by `CFBundleIconFile`), rounded and proportioned on Apple's macOS app-icon grid so Finder and the Dock show the same shape as the installed PWA instead of a full-bleed orange square. A menu-bar item uses the legacy Ciaobot face template, so macOS applies its normal light/dark tint. When the selected server reports a valid attention count, the number sits beside the face in the status bar; it is empty for zero or unknown. The menu shows the factual connection line, only the selected server's needs-you, working, and unread chats in Home's tier order with Home-style relative times and glyphs, a chat-notification status row (with a separate safe-recovery row only when opening Ciaobot is the next step), **Open Ciaobot**, a compact **Settings** submenu, and **Quit Ciaobot**. The submenu contains **Start at Login** (an explicit opt-in with macOS's real approval state; when macOS cannot use this copy, the row names the cause and the one next step), **Hide Dock Icon** (a persisted choice that keeps the menu-bar item), **Change Connected Host…**, and either **Check for Updates…** in a release build that carries the public update configuration or a truthful disabled **Updates unavailable** row in every other build. Selecting a chat opens `/chat/<id>` in the existing in-app window on the exact selected origin. The item never manages the server.

## Build and run

Requires a working Xcode or Xcode Command Line Tools Swift toolchain. From the repository root:

```sh
swift test
swift build
scripts/build-app.sh
open .build/Ciaobot.app
```

The script creates an unsigned, unnotarized local app under `.build/`; it does not install it. It copies the artwork into `Contents/Resources`, embeds Sparkle 2.10.1 from the resolved Swift Package Manager artifact in `Contents/Frameworks/Sparkle.framework`, generates `AppIcon.icns` from `Sources/CiaobotMac/Resources/app-icon.png` with the system `sips` and `iconutil` tools, and writes `CFBundleIconFile=AppIcon` into `Info.plist`. The exact square PWA artwork is kept as `Sources/CiaobotMac/Artwork/app-icon-source.png` (a byte-for-byte snapshot of `web/public/icons/icon-512.png` in the engine checkout); `app-icon.png` is generated from it by `swift scripts/make-app-icon.swift` on Apple's 1024 canvas with an 824×824 rounded tile, so it has transparent corners and the same Dock proportion as a PWA. The build never reads the engine. If the selected Command Line Tools are broken but Xcode is installed, select it for these commands with `export DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer` (adjust the path to your installation). Sparkle is an exactly pinned Swift Package Manager dependency, so the first resolve or build downloads it; later builds use the SwiftPM cache. `.github/workflows/ci.yml` runs the tests and the bundle build on a macOS runner. For a signed, archived copy to hand to another Mac, use `scripts/package-app.sh` below.

## Packaging a local ad-hoc-signed build

For a Developer ID release, use a Mac with the signing identity and either an
App Store Connect API key (preferred: no keychain item, no approval prompt) or a
`notarytool` keychain profile:

```sh
SIGNING_IDENTITY='Developer ID Application: Your Name (TEAMID)' \
NOTARY_KEY_ID='KEYID12345' \
NOTARY_ISSUER='00000000-0000-0000-0000-000000000000' \
scripts/package-notarized.sh
# or: NOTARY_PROFILE='your-keychain-profile' scripts/package-notarized.sh
```

The API key is read from `NOTARY_KEY`, defaulting to
`~/.appstoreconnect/private_keys/AuthKey_<KEY_ID>.p8`; keep it `0600` outside the
repository. Create it in App Store Connect under Users and Access → Integrations.

The script builds, signs Sparkle's nested helpers inside-out and then the app
with hardened runtime, submits to Apple, requires an Accepted result, staples
the ticket and verifies Gatekeeper and the extracted ZIP. It writes to a fresh
temporary directory, never installs the app, and does not publish a release.
The build is thin for the host architecture. Keep signing keys and
notarization credentials in Keychain, not in the repository.

Sparkle is pinned to exactly 2.10.1 in `Package.swift`; `Package.resolved`
records the resolved revision (`sparkle` 2.10.1, revision `ab7d712`).
Resolving or building needs network access the first time so SwiftPM can
download the prebuilt xcframework. The build selects the macOS slice for the
executable's architecture and copies it with its symlinks and executable helper
tools intact; an ambiguous or missing slice fails the build instead of
guessing. `scripts/build-app.sh` builds each bundle in a fresh
`.build/ciaobot-app.XXXXXX` staging directory and validates it before
publishing. Nothing is written into a pre-existing `.build/Ciaobot.app`. On
success, an existing bundle (or symlink) is renamed into a fresh
`.build/ciaobot-quarantine.XXXXXX` directory and the validated staging bundle
is renamed into `.build/Ciaobot.app`. Quarantine directories are never deleted
by the script and accumulate across builds; remove them by hand when their old
output is no longer useful. A failed build removes only its own mktemp
staging directory and leaves the previously published bundle in place. A
symlinked `.build` directory is refused before any build output is written.
The signer only accepts `APP/Contents/Frameworks/Sparkle.framework`: it
validates every nested helper's physical path and refuses any symlink outside
Sparkle's documented layout before running `codesign`. The framework is
packaged but stays inert unless the bundle carries a feed and public key:
`scripts/build-app.sh` writes them only for `CIAOBOT_RELEASE_UPDATES=1`. A
default local build has no feed URL, no scheduled check, and no installation
path; see [Automatic updates](#automatic-updates).

The copy and signing helpers trust the app-bundle location their caller names,
and secure everything inside that bundle: a link placed in the bundle cannot
redirect a copy, a signature or a deletion elsewhere. A caller that reaches the
bundle through a symlinked ancestor has chosen that physical destination, so the
build and packaging scripts always pass a freshly created physical path
(`.build/ciaobot-app.XXXXXX`, a fresh packaging output, or a fresh quarantine
directory) rather than an existing tree.

`scripts/package-app.sh` turns the built bundle into an ad-hoc distributable for personal testing:

```sh
scripts/package-app.sh                                       # build, sign, archive into a fresh temp directory
scripts/package-app.sh --output ~/Desktop/ciaobot-package-1   # a new or empty artifact directory
scripts/package-app.sh --no-build --app .build/Ciaobot.app    # package an existing bundle
```

It runs `scripts/build-app.sh` first unless `--no-build` is given (so the same `DEVELOPER_DIR` note applies), copies `.build/Ciaobot.app` into the output directory, strips quarantine, signs Sparkle's nested helpers inside-out and then ad-hoc signs the copy (`codesign --force --sign -`, the same identity the retired Tauri desktop used through `bundle.macOS.signingIdentity: "-"`), normalises timestamps, verifies it with `codesign --verify --deep --strict`, archives it as `Ciaobot-<version>-adhoc.zip` with symlink-preserving `zip -X -y`, unpacks that archive into a temporary directory and verifies its signature, CDHash, executable and Sparkle layout a second time, then writes `MANIFEST.txt` (bundle identifier, version, exact executable architectures, CDHash, Gatekeeper assessment, hashes) and `SHA256SUMS`. It never installs, replaces, or launches an app, never writes inside an Applications folder, never contacts the server, and signs a copy, so a build that is already running is left alone. There is no force option: a non-empty `--output` is refused instead of replaced, so an existing `Ciaobot.app`, ZIP, `SHA256SUMS` or `MANIFEST.txt` is never overwritten. An output directory that contains the source app, or that lives inside it, is refused as well, so a mistyped path cannot delete or corrupt the build. Use a new directory (or the default fresh one) for each run. `MANIFEST.txt` describes the artifact without recording any local filesystem path.

Verify an artifact by hand:

```sh
shasum -a 256 -c SHA256SUMS
codesign --verify --deep --strict -vv Ciaobot.app
codesign -dv --verbose=4 Ciaobot.app    # Signature=adhoc, Identifier=local.ciaobot.mac
```

What this build is not:

- There is no Developer ID signature and no notarization. `spctl --assess` rejects it, and `MANIFEST.txt` records that. On another Mac, Gatekeeper blocks the first launch of a quarantined copy: allow it once in System Settings > Privacy & Security > Open Anyway, or run `xattr -dr com.apple.quarantine Ciaobot.app` on the extracted copy. The old right-click > Open shortcut no longer bypasses Gatekeeper on current macOS.
- There is no automatic updater in this ad-hoc build: no `SUFeedURL` and no `SUPublicEDKey` are written unless `CIAOBOT_RELEASE_UPDATES=1`, so the in-app **Updates unavailable** row stays disabled and no feed is contacted. A release build does check for updates (see [Automatic updates](#automatic-updates)), but it installs only a notarized, EdDSA-signed archive, so this unnotarized ad-hoc ZIP is not a valid update payload and must never be published as one.
- The bundle identity is fixed at `local.ciaobot.mac` (`CFBundleIdentifier` in `scripts/build-app.sh`). Do not change it: WebKit's on-disk stores, saved sign-in (`~/Library/Application Support/CiaobotMac/session-stores.json`) and notification permission are tied to it, and macOS treats a different identifier as a different app.
- The packaged executable is built for the build machine's CPU architecture. `MANIFEST.txt` records the exact value in `architectures` (for example `architectures=arm64` on Apple silicon, or `architectures=x86_64` on Intel), and the script prints it. This is a **thin** app, not a universal binary: an `arm64` build is Apple silicon only and an `x86_64` build is Intel only. The script neither builds nor claims a universal binary, and it does not verify any other architecture.
- Ad-hoc signing proves the bundle was not altered after signing, not who built it. Every rebuild has a new CDHash, so macOS sees a new identity for notification permission; notification delivery from an ad-hoc build and Start at Login approval are not verified by this script and remain manual checks. An ad-hoc build carries no Developer ID team, so its Start at Login row says the signed release is required instead of offering a registration macOS would refuse.
- Reproducibility covers packaging only: fixed timestamps and symlink-preserving `zip -X -y` make the archive repeatable for identical file content, but the Swift toolchain does not promise bit-identical binaries across builds.

## Automatic updates

Ciaobot for Mac updates itself with the Sparkle 2.10.1 framework that is
already pinned and packaged. Only a build that opts in embeds the updater
configuration:

```sh
CIAOBOT_RELEASE_UPDATES=1 scripts/build-app.sh
```

The four public values live in `release/update-config.env`:
`UPDATE_FEED_URL` (`https://github.com/raffaelefarinaro/ciaobot-mac/releases/download/updates/appcast.xml`),
`UPDATE_PUBLIC_ED_KEY` (the project's EdDSA public key),
`UPDATE_MIN_SYSTEM_VERSION`, which has to match `LSMinimumSystemVersion`, and
`UPDATE_TEAM_ID`, this project's Apple team identifier. The
build refuses an http feed, a credential-bearing URL or a key that is not a
base64 EdDSA public key. Nothing secret is committed: the EdDSA private key
lives only in the operator's keychain and is never read by the build.

A flagged build writes `SUFeedURL`, `SUPublicEDKey`,
`SUEnableAutomaticChecks`, `SUAutomaticallyUpdate`,
`SUAllowsAutomaticUpdates`, `SUScheduledCheckInterval` (one hour),
`SUVerifyUpdateBeforeExtraction`, `SURequireSignedFeed=false` and
`SUEnableSystemProfiling=false`. Without the flag the `Info.plist` has no feed
and no key, so no updater object is created, the menu keeps its disabled
**Updates unavailable** row, and the client never contacts the feed. Debug
builds and test launches are inert as well: a DEBUG build never allows
updates, a process with `XCTest*` variables is refused, and only the bundle
identifier `local.ciaobot.mac` may update itself.

The client creates one retained updater at launch. It starts it once, runs a
single background check immediately when automatic checks are on, and lets
Sparkle keep checking hourly afterwards. Archive signatures are mandatory: the
archive's EdDSA signature and notarization are verified before extraction, so
a tampered or unnotarized download is never unpacked. The immediate-install
delegate (`updater(_:willInstallUpdateOnQuit:immediateInstallationBlock:)`)
returns `true` and runs Sparkle's install handler on the next main-queue turn,
so a verified update installs and relaunches straight away instead of waiting
for the user to quit. **Only the Mac client restarts.** The Ciaobot engine and
the web app it serves are separate processes and keep running; this client does
not restore its own web view's unsaved drafts.

The first updater-enabled build has to be installed by hand once, because an
installed 0.1.1 has no updater. Installing this client over an existing copy
keeps the fixed bundle identifier, so WebKit stores, saved sign-in and
notification permission survive.

Publishing an appcast is a separate, deliberate step:

```sh
SIGNING_IDENTITY='Developer ID Application: Your Name (TEAMID)' \
NOTARY_KEY_ID='KEYID12345' \
NOTARY_ISSUER='00000000-0000-0000-0000-000000000000' \
scripts/package-notarized.sh

scripts/make-appcast.sh \
    --archive /path/to/Ciaobot-0.1.2-notarized.zip \
    --download-url https://github.com/raffaelefarinaro/ciaobot-mac/releases/download/updates/ \
    --output appcast.xml
```

`make-appcast.sh` refuses a non-https or credential-bearing prefix, an existing
non-empty output, a wrong `CFBundleIdentifier`, a version in the archive name
that disagrees with the bundle, and a non-arm64, invalidly signed, unnotarized
or Gatekeeper-rejected archive. It also refuses an archive that this project
did not sign: `codesign -d` has to report `TeamIdentifier=AXBFS96Y9F` from
`release/update-config.env` and a `Developer ID Application` authority, so a
valid, notarized app from another developer can never be republished under this
project's Sparkle key. The team check runs before the appcast is generated. It
runs Sparkle's pinned `generate_appcast`, so archive signatures are produced by
the tool and never written by hand. It only writes the local appcast file;
uploading `appcast.xml` and the archive to the `updates` release tag is manual.

Feed signing (`SURequireSignedFeed`) is deliberately off for this first
release. The archive signature plus notarization authenticate the installed
code, while a mis-signed feed would stop updates entirely. Enabling it is a
recorded follow-up, along with key rotation and delta updates.

## Tests, including the GUI launch test

`swift test` runs unit and integration tests. The GUI launch test starts the real debug app against a private HTTP fixture bound to an ephemeral `127.0.0.1` port, then checks that:

- a native window of the expected size exists;
- the app probes `/api/startup-status` on that fixture;
- WebKit loads the fixture page and runs its same-origin navigation;
- a scripted same-origin `target=_blank` request is blocked before it can open a child window.

The fixture is created inside the test and has no relationship to the operator's Ciaobot server. The test never types into the address field, never uses accessibility automation, and never contacts the proposed `127.0.0.1:8443` address. It runs as part of the default debug `swift test`; CI does not set an environment variable to skip it. A release test run reports the GUI launch test as an explicit skip because it relies on the DEBUG-only fixture launch controls; the release app still builds and the in-process WebKit delegate tests still run.

`AppAssetsTests` proves the original face artwork, the exact PWA source artwork, and the legacy tray template are bundled byte-for-byte (SHA-256 pinned) and resolve from the SwiftPM debug products, the Xcode build system's `Contents/Resources` resource bundle, the `swift test` bundle, and a release `.app` layout. It also checks that the shipped app icon has an alpha channel, transparent canvas corners and tile corners, an opaque 824×824 tile centred at (100,100) on the 1024 canvas, the PWA orange fill, and the PWA face inside it, so a square or redrawn icon fails the suite. ## Connecting safely

The initial address is a same-Mac candidate, not proof of identity. Enter an origin without a path, query, fragment, or credentials; one ordinary trailing slash (`https://example.com/`) is accepted and normalised to the same canonical origin. HTTP is accepted only for `localhost`, `127.0.0.1`, and `::1`; all other hosts require HTTPS. Hosts are compared literally, so `localhost` and `127.0.0.1` are different origins. The app checks `/api/startup-status` without credentials, rejects redirects, and requires a successful JSON response with a nonempty `startup_id`. This checks protocol shape **not server identity**; verify that you trust the address before signing in. TLS uses the system's normal certificate validation.

While the connection screen is shown, a production build may also check the one fixed candidate `http://127.0.0.1:8443` with that same credential-free probe. It reports only **Local server responded** or **No local server detected**, with a manual **Check Again**. The result is a hint: it does not identify the server or who runs it, no startup identifier, process, lock, or startup record is treated as authentication, and the check never navigates, signs in, scans ports, or changes the address. Automatic checking is disabled in debug builds and test launches; the debug app checks only on an explicit click, and the automated tests inject a fixture candidate and transport instead of contacting the real address.


The probe is deliberately credential-free: it uses an ephemeral session, discards caller-supplied additional headers, ignores cookie and credential stores, does not follow redirects, bounds the response body, and times out. A server authentication challenge other than normal TLS server-trust validation cancels the probe.

The web login can keep a session across launches. **Keep me signed in on this Mac** starts on whenever persistence can actually work: an HTTPS address on macOS 14 or later while the mapping file is usable. When the system or the file cannot support it — HTTP, macOS 13, or an unusable mapping file — the toggle starts off, stays disabled, and the connection screen says why. An explicit click wins for the current address only: changing the address or the server clears it and returns the toggle to this default, so consent is never inherited by another host. HTTP (including loopback) and older systems always use an in-memory store. The app never uses WebKit's default shared store. Each canonical origin (scheme, literal host, and effective port) maps to its own `WKWebsiteDataStore(forIdentifier:)` with a randomly generated UUID. That isolates which top-level view uses a cookie jar, **not** individual requests: WebKit cookies are scoped by host, not port, and the navigation delegates never see subresource loads. A page loaded from the selected origin can therefore request an image, script, or `fetch` from another port on the same host, and WebKit sends the same-host cookies with that request. The app cancels cross-origin subframe navigations and blocks HTTPS-to-HTTP downgrades, but it does not claim subresource isolation. The mapping lives in `~/Library/Application Support/CiaobotMac/session-stores.json` (directory `0700`, file `0600`) and contains only origins and identifiers; it never contains cookie values, and the client never logs them. (The menu-bar feed separately copies only `ciao_session` into an in-memory request for the exact selected origin; see **Menu-bar chat authentication**.) A named store persists all of that origin's WebKit website data, not only cookies (for example local storage); **Forget saved sign-in** asks WebKit to remove the store and verifies it is no longer listed. The app does not inspect WebKit's on-disk bytes, so "removed" means "WebKit no longer lists or serves it", not a forensic wipe. TLS is WebKit's and the system's normal validation.

Persistent sign-in does not connect on its own. The app still opens on the connection screen, the probe still runs without credentials, and the **Keep me signed in** choice is not stored as a preference: each launch recomputes the default from the address, and turning it off lasts for this process and that address only. **Change Server** clears the choice as well, so the next connection starts from the default rather than inheriting the previous host's choice. Connect (including Return) and forget share one task gate, so a probe cannot start while forget is running and forget cannot start while a probe is running. If a requested persistent session still cannot be honoured (for example, the mapping file becomes unwritable at connect time), the session window shows a notice instead of silently keeping the session in memory. **Forget saved sign-in** on the connection screen first re-checks that the mapping file still matches the snapshot this process loaded, then waits until the connection's `WKWebView` weak reference is actually nil, then removes the named WebKit store through `WKWebsiteDataStore.remove(forIdentifier:)`. WebKit can refuse a removal while the store is still cached, so the call is retried a few times with a short delay; success is still only reported once the identifier is actually absent from WebKit's list, and the mapping is only deleted then. The app does not claim the view was released unless the tracker observed the deallocation; if the view never releases, forget is not attempted and says the session view is still closing. If WebKit keeps refusing because the store is still in use, or the mapping cannot be rewritten, the mapping is kept so the operation can be retried. If the map write fails after WebKit reported the store removed, the identifier is retired for the rest of the process so the removed store is never reopened; retrying completes the removal. Every identifier lookup also verifies the on-disk snapshot first, so a mapping removed (or removed and re-created) by another copy is never reopened from this process's cache. If another copy of the app changed the mapping file after this process read it, writes are refused rather than overwriting the other mappings: persistence fails closed with a restart message. If the mapping file is unreadable, ambiguous, or contains an entry the app would never write (for example, two origins sharing one identifier, a non-canonical origin, or an HTTP origin), persistence fails closed: the app uses ephemeral stores and does not open any saved store. The file is the only record of which stores the app can remove, so the UI warns against deleting it.

The menu-bar status line is intentionally factual and minimal: **Not connected** before a verified connection, then **Connected to** the exact canonical origin. When the feed's validated `attention_count` is positive, that number is drawn beside the face in the status bar; zero, a missing count, a non-matching origin, or a disconnect leaves the face unnumbered. The chat section below it comes only from `GET /api/menubar-chats?limit=12` on that origin, filtered to the chats Home would show above its quiet tier. Rows keep Home's tier order (needs you, working, unread) with Home's precedence (a needs-you chat appears once, even when it is also unread or running; an unread chat appears above working even while it runs), but the menu no longer repeats that order as headers: each row shows Home's compact relative activity unit (`now`, `5m`, `2h`, `3d`, `1w`, `1mo`) and a template glyph matching the homepage signal: an alert triangle, a 3×3 grid, or an eye. A missing or unparseable `last_activity_at` leaves the time off rather than showing "now". Ordinary read, idle chats are not listed; the menu still offers **Open Ciaobot** for the full list. Working state comes from the tray's own authenticated `/ws/events` subscription (the server's `snapshot.active_streams`, `chat_streaming_started`, `chat_streaming_done`, and `chat_result_ready`), independent of the notification opt-in: notifications can be off, denied, or unavailable and the working tier still updates. Events before the snapshot are ignored, a close clears working state, and a new snapshot is the baseline after reconnect. When that feed is not live, the menu says **Working status connecting…** or **Working status unavailable** / **… sign in** and does not render a working row or claim "no agents working". Untrusted titles and workspace names have control/format characters and line breaks removed and are length-bounded, so one row cannot forge another; the workspace is secondary text in the row tooltip. The status-bar badge and tooltip use the server's `attention_count` only when it is non-negative and compatible with the rows; when the count is missing, wrongly typed, or inconsistent, the valid rows remain and no number is shown. The tooltip adds a working count only from those same live, listed rows. When the server returns 401/403, or a remote origin has no `ciao_session` cookie in its own WebKit store, the menu says **Sign in to see chats** and shows no count. A structurally malformed response says **Chat list unavailable**; the client does not invent chats or zeroes. The list refreshes when the menu opens (throttled) and every 30 seconds while connected. Closing the main window leaves the client and its refresh timer running in the menu bar; **Open Ciaobot** (or clicking the Dock icon) brings back the same window and connection rather than starting a second connection. Selecting a chat presents the window and loads `/chat/<id>` on the exact origin; if no web view is attached yet, one pending path is queued and loaded when it attaches, and a selection that cannot be accepted shows an explicit alert rather than doing nothing. An id that is not one safe path segment is shown disabled. **Quit Ciaobot** calls `NSApp.terminate` only: it sends nothing to the server and the separately installed server keeps running.

The Dock icon carries the same attention count as the menu-bar face. Both read the one loaded chat snapshot, so they can never disagree: a positive count is drawn on the Dock tile, and a zero count, a missing count, an unavailable chat list, or a disconnect clears the badge instead of leaving a stale number. The Dock badge never fetches, counts, or polls anything by itself.

## Menu-bar chat authentication

The local endpoint is reachable without a session only from a loopback peer. A loopback connection still offers its exact per-session `ciao_session` cookie when its own WebKit store has one (a local reverse proxy may require it), but it does not require the cookie and never claims the session is signed in merely because rows loaded. A remote origin requires that cookie: the client reads it from the connection's own `WKWebsiteDataStore` (the named store this connection uses, or the connection's nonpersistent store), filters it by the exact request host, path, scheme, and expiry, and attaches only that cookie to an ephemeral URLSession request. The tray's working feed uses the same selection and the same exact-origin rule for the `/ws/events` handshake; it is a separate socket from native notifications, so working state does not depend on the notification opt-in. The client never uses `WKWebsiteDataStore.default()`, never logs or persists the value, and never lets URLSession add ambient cookies, credentials, cache, or headers. Redirects are refused rather than followed, including same-origin redirects, so the credential cannot be carried somewhere the user did not choose; the final response URL is also re-checked against the exact origin and fixed endpoint. TLS uses the system's normal server-trust validation, and any non-server-trust authentication challenge cancels the request. The client does not read a lock file, startup id, or process record as identity; `/api/startup-status` remains only the pre-connection protocol-shape check.

These protections are tested against isolated loopback fixtures and injected WebKit stores. They do not constitute a live end-to-end test of a remote authenticated server: the remote path is implemented, but the test suite never contacts the operator's Ciaobot installation or any remote server. The endpoint's own loopback/session policy still belongs to the server, and this client does not manage or restart it. WebKit cookies are host-scoped, not port-scoped, and subresource loads are not visible to the app, so the feed inherits the web view's documented same-host subresource limitation: a page from the selected origin can request a subresource that sets a cookie for that host. The feed still selects only `ciao_session` and sends it only to the exact selected origin, but it cannot add subresource isolation the web view does not have.

## Native chat notifications

Native banners are opt-in and separate from the web UI. The **Settings → Turn On Chat Notifications…** row is the only path that can call `UNUserNotificationCenter.requestAuthorization`; launch and connect never prompt. Enabling stores one boolean (`CiaobotChatNotificationsEnabled`) in the app's UserDefaults; it does not store an origin, cookie, or chat title. Disabling turns the row off and cancels the socket. The notification row keeps that explicit enable/disable action in every off/on state, so a recovery action never replaces the user's opt-out. Denied and unavailable states are not opt-in states: their row either opens Settings when macOS is the blocker or stays disabled with the reason. The notification row and its recovery row live only in the Settings submenu and are never repeated at the top level; Settings is present even when notifications are the tray's only provider.

The Settings notification row's visible title names the condition. **Chat Notifications On** appears only after the authenticated event stream has delivered its snapshot; otherwise it reads **Notifications on — connecting…**, **Notifications on — reconnecting…**, **Notifications on — connect to a server**, **Notifications on — sign in to receive**, **Notifications on — server refused app authentication**, **Notifications on — server rejected this app's origin**, **Notifications on — event stream redirected; not followed**, or **Notifications on — unexpected server event**. When opening Ciaobot is the next safe step, a separate row beside it offers **Connect in Ciaobot…**, **Open Ciaobot to Sign In…**, or **Open Ciaobot to Check the Server…**; these never go to System Settings and never retry with a credential. A transport-level close may say reconnecting and retry with the bounded backoff; refused authentication, a rejected origin, a refused redirect, and an undecodable event do not claim to reconnect and do not retry automatically. Opening the menu may make one manual retry on the same selected origin.

**Notifications blocked by macOS — Open Settings…** appears only when `getNotificationSettings` actually reports `.denied` (or an explicit request returns not-granted without an error), and opens the fixed Notifications pane. It is distinct from **Notifications allowed but turned off in macOS — Open Settings…**, which appears when macOS reports `.authorized` (or `.provisional`) but both the app's alert setting and its Notification Center setting are `.disabled`: permission exists, yet no banner or Notification Center entry would ever appear, so the row never claims "On". Both blocked rows open the same fixed Notifications pane and say to select Ciaobot and allow banners; their tooltips also say that Focus must be off, because Focus has no public API and the app cannot detect it. A technical request error is preserved as **Notifications unavailable — registration failed; use signed Ciaobot.app** with the exact macOS message in the tooltip; the client says it cannot tell whether the build is unsigned, rather than asserting it. A process without an app bundle reads **Notifications unavailable — bare executable; use Ciaobot.app**. An unrecognized macOS authorization status reads **Notifications unavailable — unknown macOS permission state**. Those unavailable states stay disabled because no in-app action can create a notification identity macOS does not have.

While notifications are on and the app is connected, the client opens the `/ws/events` socket the server already exposes, on the exact selected origin (`ws` for HTTP, `wss` for HTTPS). The handshake carries an explicit exact `Origin` and a single `Cookie: ciao_session=…` selected from this connection's own `WKWebsiteDataStore` for the exact URL. It never uses the default WebKit store, URLSession cookie storage, a credential store, a cache, Authorization, or additional headers. If the store has no usable session cookie, no handshake is attempted; a later menu open or bounded retry re-reads the store, so finishing the web sign-in recovers without a new opt-in. Redirects are refused rather than followed, and only normal TLS server-trust validation is accepted; any other authentication challenge cancels the handshake. The socket is cancelled when the connection changes, the app disconnects, notifications are turned off, or the menu-bar item is torn down.

The server sends a `snapshot` before other events. The client treats that as a baseline: it never turns the snapshot's `active_streams` or any event received before it into a notification. After a reconnect the next snapshot is a new baseline, so nothing from the gap is replayed. A `chat_result_ready` after the snapshot produces one banner; an identical result delivered twice for the same turn is suppressed, including if a duplicate arrives after a reconnect, and a new `chat_streaming_started` (or a snapshot showing that chat streaming) allows a genuinely repeated answer to notify again. Each notification uses a stable identifier for the origin and chat, so two servers cannot overwrite each other's banner. Titles and snippets are cleaned and length-bounded exactly like menu text, and the notification's payload contains only the chat id and canonical origin.

Clicking a banner is only a navigation request. Only the default click action is handled; dismiss, clear, and custom actions never navigate. On a normal click the existing window is presented and the same-origin `/chat/<id>` loads when the app is already connected to that exact origin. A click that arrives on a cold launch, or while disconnected or connected to another origin, presents the window and retains one validated target in memory: it never signs in, opens an event socket, sends a credential, autoconnects, or navigates another origin. The retained target is consumed only when the user manually connects the exact canonical origin from the notification and the matching web view attaches; until then it does nothing. The notification payload contains only the chat id and canonical origin, and both are re-validated before any navigation. Notifications do not run when the app is quit, do not fetch in the background, and do not control the server process.

`chat_result_ready` does not carry a chat helper kind. The engine publishes it for ordinary chats and also for its own post-archive memory pass, while suppressing only the OS push for a memory pass (the event still travels over `/ws/events`). The PWA can suppress its in-app toast because it correlates the event with an authenticated `/api/chats` record whose `helper.kind` is `memory_pass`; this client does not fetch that record for the event. It therefore does not guess from a title: a user chat may legitimately be called "Memory pass", and a title-prefix filter would silently hide real replies. Every authenticated `chat_result_ready` is treated as a chat completion, including a memory-pass completion, until the server provides a helper kind on the event or this client adopts an authenticated helper lookup. This is an intentional, documented limitation rather than a claimed suppression.

The client does not collect passwords or expose a general native shell/filesystem bridge to web content. File uploads use a native open panel that returns only the files the user selects; downloads use a native save panel. Both are user-mediated and available only to same-origin frames.

Two small scripts are injected: the historical constant `window.__CIAOBOT_DESKTOP__ = true` marker (main frame only, so the web UI chooses Mac keyboard shortcuts) and a one-way trusted-click signal. The signal carries no page data and grants no native capability; it is used only to decide whether a new-window or external-link request followed a real click. It is a user-intent guard, not a security boundary against a compromised selected origin.

One stylesheet is injected into the main frame. It exists only in this client: the PWA in a browser never receives it, and nothing in the engine or the PWA changes. It does two limited things, using only the page's existing theme class and `--*` colour variables; it carries no page data, adds no message handler, and offers no native capability.

The first is the scrollbar theme. WebKit paints a scroll container's scrollbar from the page's **used `color-scheme`** when the system is set to always show scrollbars ("Show scroll bars: Always", i.e. legacy scrollers). The engine declares no `color-scheme`, so a dark page in a dark window still gets the light system track: that is the white sidebar scrollbar. The client declares `color-scheme: dark` and switches it to `light` from the page's own `theme-light` class, so the native scroller follows the engine theme. The `::-webkit-scrollbar` rules used earlier did not change it. In current WebKit they are disabled by the page's `scrollbar-width: thin` on every element, and Safari does not implement `scrollbar-color` (18.2 added only `scrollbar-width` and `scrollbar-gutter`). The client still declares the standard `scrollbar-color` with an opaque `var(--bg)` track, so an engine that gains support paints a page-coloured track rather than the page's `transparent` one that exposed the host's white; it is inert in today's WebKit.

The second is the Home setup card. Its install row says "Use your browser's Install option in the address bar or menu", instructions this window cannot follow: the client is not a browser and cannot install the PWA. Its notifications step is redundant with the client's own native notifications, and its phone-setup link also exists under Settings → Access & devices. The stylesheet therefore hides that setup card while it is in the browser-instructions state, keyed on the card's own `.home-setup` class and its `/settings#install-app` link. A card that still offers a real install prompt (no such link) is left alone, and no other Home card is matched. A renamed component only brings the card back; it cannot hide unrelated content.

Navigation is confined to the exact selected origin (scheme, host, and effective port). User-initiated external HTTP, HTTPS, and mail link activations (including `target=_blank` links) open in the system browser, except HTTPS-to-HTTP downgrades are blocked. Other schemes and URLs with credentials are blocked. Script-initiated `window.open()` without a user activation is refused.

Same-origin images, PDFs, and downloads open in a transient app-owned child window: images and PDFs render there, downloads use a native save panel, and the request keeps the connection's cookie store because it is the exact selected origin. That child refuses every non-origin navigation, including redirects and scripted navigation. External link activations from the main window go to the system browser, never to a webview holding the session store.

`createWebViewWith` uses the WebKit-provided configuration, copied with a fresh user content controller so the child does not inherit the main frame's scripts or gesture bridge. WebKit requires that configuration: returning a webview with a different `websiteDataStore` crashed `createNewPage` in investigation, so a JS popup child cannot be cookie-isolated with public API. A child therefore shares the connection's store, which is safe because the child is restricted to the exact selected origin and the store itself is per-origin. The OAuth placeholder decision path (`about:blank` after a gated `window.open`) shares that store but never loads the external authorization URL: the URL is handed to the system browser and the child closes. The blank-window handoff is tested with a test-only popup setting and a seeded activation; production's real user-gesture/popup-blocker behavior remains unverified. The app has one main window plus these transient content/sign-in windows, and a **Change Server…** command (Command-Shift-L) for recovery. Changing the server dismantles the WebView and returns to the connection screen; if the initial page fails to load, the app returns there with an error.

## Tray settings

Every secondary control lives in the single **Settings** submenu below **Open Ciaobot**: the notification status row and its recovery row, Start at Login, Hide Dock Icon, Change Connected Host, and Updates. The submenu is created whenever any of those controls exists, so a tray whose only provider is notifications still has Settings; no control is duplicated at the top level and the submenu adds no leading, trailing, or doubled separator. Opening the menu or the submenu only re-reads OS state; it never requests notification permission.

**Start at Login** is a per-user, explicit choice with two requirements: the app must be installed in `/Applications` (a copy running translocated from a download or a mounted disk image is not installed), and the build must be Developer ID signed (an ad-hoc build is not). The app reads `SMAppService.mainApp.status` when the menu opens but calls `register()` only from a click on that row; launch, connection, and menu opening never enable it. The row is **Start at Login** with a check mark only for `.enabled`. `.requiresApproval` is shown as **Start at Login — Approval Needed…**, is not marked on, and opens the fixed Login Items pane in System Settings. When macOS cannot use this copy, the row names the actual cause instead of a generic unavailable state: **Start at Login — Move Ciaobot to Applications…** for a bundle outside Applications, **Start at Login — Needs the Signed Release…** for a build with no Developer ID team, and **Start at Login — macOS Cannot Find Ciaobot…** for an installed, signed app macOS does not list. Only that last cause — the one Login Items can settle for an app that is already installed and signed — offers **Open Login Items Settings…** in its explanation; the other two name the step that actually fixes them: move the app into Applications, or install the signed, notarized release. A bare `swift build` executable keeps **Start at Login Unavailable** without touching ServiceManagement. Clicking any of those rows only explains the one next step: it never registers, never unregisters, and never claims Start at Login is on. A thrown registration error is surfaced as **Start at Login Failed** with the system's reason; a thrown stop stays **Start at Login — Stop Failed** and retries the stop rather than turning the next click into an enable. The row never claims the OS status changed unless `SMAppService` reports it. This repository builds an unsigned, unnotarized local app, so a local build reports the signed-release cause rather than claiming success. The app installs no launch agent or helper of its own.

**Hide Dock Icon** is stored as one boolean (`CiaobotHideDockIcon`) in the app's UserDefaults. It hides the Dock only while the main window is closed: an open window is always `.regular` so it can become key and appear in the normal app switcher; when the main window closes, the saved `.accessory` policy hides the Dock and leaves the menu-bar status item in place. Turning the row on while the window is open keeps `.regular` until that window closes. **Open Ciaobot** restores `.regular` without changing the saved preference, miniaturized windows are deminiaturized before they are ordered, and turning the row off restores `.regular` immediately. The saved choice is applied after the initial window has had a chance to appear, so launch itself does not hide an open window's Dock icon. This is a local presentation preference, not a server or workspace setting.

**Settings → Change Connected Host…** is enabled only after a verified connection. It presents the client window and only then posts the same request as **Change Server…** (Command-Shift-L); if the window cannot be presented, the presenter shows an explicit failure and this action does not post a request that would be silently dropped. The connection screen returns and the previous connection is dismantled locally. It never contacts, stops, restarts, or reconfigures the separately installed server. The connection screen returns **Keep me signed in** to its default instead of carrying the previous host's choice, so signing in to a different host starts from a fresh default.

**Settings → Check for Updates…** appears only in a release build that carries an updater configuration, and is enabled only while Sparkle reports it is idle; clicking it asks Sparkle to check and show its own progress. Its tooltip states that an automatic update restarts this Mac client only. In every other build the row keeps its truthful disabled shape: **Updates unavailable**, with the exact reason in its tooltip (no feed, no signing key, a debug or test process, or a foreign bundle identifier), and no action. Opening the menu never starts the updater or a check.

When macOS actually denies notifications, the blocked row inside **Settings** shows that in its title and opens the fixed app-owned URL `x-apple.systempreferences:com.apple.Notifications-Settings.extension`. The same fixed link is offered by the allowed-but-delivery-off row, and by no other state. It is never supplied by a server or a page, and it is not offered for a technical registration error, a missing sign-in, or a missing connection: those visible states name the missing step and offer either the signed/bundled app or the Ciaobot window instead. When notifications are unavailable because the process is not a bundled app, no Settings action is offered, because System Settings cannot turn that process into a notification-capable app.

## Known limitations

- Persistent sign-in is available only for HTTPS origins on macOS 14 or later, and **Keep me signed in** starts on exactly there. HTTP, macOS 13, and an unusable mapping file keep it off and the toggle disabled; HTTP and macOS 13 always use in-memory stores, and the app never connects automatically.
- The **Keep me signed in** choice is not stored as a preference, so each launch recomputes the default from the address: a saved session is used when the box is on (the default for a supported HTTPS address) and not after it has been turned off for this run. An explicit choice applies only to its address and is cleared when the address or server changes. This is deliberate: no saved origin is turned into a launch target.
- Persistent sign-in stores the session in WebKit's on-disk website data, protected by normal user file permissions (and FileVault if it is enabled), not by the Keychain. Any process running as the same user can read it, so this protects against another account or a stolen offline disk, not against local malware already running as the user.
- Each canonical origin has its own store, so signing in on one port or scheme does not sign in on another. This is what keeps cookies (which ignore ports) from crossing origins, at the cost of separate sessions per origin.
- Forget is gated on evidence: it re-checks the mapping snapshot, waits until the connection's tracked `WKWebView` is deallocated before erasing, and if a view still uses the store WebKit refuses the removal after a few bounded retries (observed: the store stays listed and the mapping is retained). The app does not claim the view was released without observing that. A successful store removal with a failed mapping write retires the identifier for the rest of the process; the record is kept for retry and the id is not reopened in that process. **Retirement is in-memory only**: after a restart the retained record is used again. WebKit reported the store removed before the write failed, but the app verifies that through WebKit's store list, not by inspecting the on-disk directory, so it does not claim the bytes are unrecoverable. An in-flight cookie write at the exact moment of forget remains a WebKit-internal edge case; retrying forget is safe.
- Per-origin stores isolate top-level views, not subresource requests. WebKit cookies are host-scoped and the navigation delegates never see subresource loads, so a page from the selected origin can request a resource from another port on the same host and send the same cookies (verified against a real fixture). The app does not promise subresource isolation.
- Two copies of the app can change the mapping file. Every identifier lookup re-reads the file and fails closed if it no longer matches the snapshot this process loaded, so a mapping another copy removed (or removed and re-created) is never reopened from cache. Every write takes a non-blocking advisory file lock (a mutex only, never authority), re-reads the exact bytes, and refuses the write if they differ; a held lock fails immediately instead of blocking the main actor. A writer that ignores the lock is still caught by the content comparison.
- If the mapping file is corrupt, maps two origins to one identifier, or contains an entry the app would never write (non-canonical or HTTP), persistent sign-in is disabled and no saved store is opened. The file is the only record of which named stores this app owns, so the UI does not advise deleting it: deleting it would lose the ability to remove existing saved session data through the app. Repairing or restoring it is the supported recovery; until then, data already written to named stores can remain on disk.
- The trusted-click signal is page-visible to the selected origin. A compromised server could synthesize it; native origin, scheme, cookie-store, and destination checks still apply. WebKit exposes no public native user-gesture flag for `window.open`.
- Script-initiated `window.open()` without a user activation is refused. The actual blank-window OAuth handoff is tested with the test-only popup setting and a seeded activation; production's real user-gesture/popup-blocker behavior remains unverified, so full OAuth is not claimed.
- JS popup children cannot be given a separate cookie store: WebKit requires the configuration supplied to `createWebViewWith`, and changing its `websiteDataStore` crashes `createNewPage`. The child shares the connection's per-origin store but is restricted to that origin and never loads an external URL.
- For a remote feed, the existing `ciao_session` cookie is copied from the connection's WebKit store into an in-memory `URLRequest` header for the exact origin. The client does not log, persist, or reuse that value elsewhere, and it refuses redirects and non-server-trust authentication challenges. URLSession and the operating system may still hold transient request bytes in memory while the request is in flight. The remote authenticated path is implemented and unit/isolated-fixture tested, but not verified end to end against a real remote server in this slice.
- A loopback feed may also carry its own `ciao_session` when the connection's store has one, which covers a local reverse proxy. Loading local rows is not presented as a signed-in state; a 401/403 shows **Sign in to see chats**, and the status line remains only **Connected to** the selected origin.
- The menu-bar chat feed is a read-only view of the endpoint the server already exposes. It has no background agent, installer, updater, or server lifecycle management. Native notifications and the tray's working feed are separate event sockets; neither changes the feed's read-only policy. Remote authenticated feeds rely on the existing `ciao_session` cookie in the connection's WebKit store; a server that changes its cookie name or auth mechanism will show **Sign in to see chats** until this client is updated.
- Native notification delivery, the macOS permission sheet, and a real banner click are not automated. The tests inject a fake permission centre and exercise the real WebSocket transport against an isolated loopback fixture; no test asks the operator's Mac for notification permission or posts an OS banner. The delegate's gate is unit-tested to accept only the default action and refuse dismiss/custom actions, but delivery of a real `UNNotificationResponse` remains a manual check with the sealed, ad-hoc signed `Ciaobot.app` produced by `scripts/package-app.sh`, not with the unsigned `.build/Ciaobot.app` from `scripts/build-app.sh`.
- Notifications are live-only: the socket exists while the app is running and connected, and nothing is fetched or queued while it is quit or disconnected. A completion that happens during a gap is not replayed from the next snapshot. Turning notifications off does not remove banners already delivered to Notification Center. Clicking one retains a validated same-origin target if the app is disconnected; it is opened only after the user manually connects that exact origin and the matching web view attaches. It never autoconnects or sends credentials by itself.
- The notification status row keeps the explicit enable/disable action whenever notifications are off or on. When a sign-in, connection, or server check is the next safe step, a separate focused row opens Ciaobot; it never changes the notification preference, follows a redirect, or retries with a credential on the user's behalf. This is one extra row only in those states, not a modal, hidden modifier, or tooltip-only action.
- Focus / Do Not Disturb has no public API. Ciaobot never reports an active Focus session as a notification problem and never guesses one from delivery behaviour; the blocked-state tooltips say Focus must be off and that the app cannot detect it.
- An allowed permission with both visible delivery channels disabled is reported as a blocked state, not as "On". The snapshot covers authorization, alert setting, and Notification Center setting; scheduling style, sounds, and Focus are outside it.
- A memory-pass completion still appears as a native banner. The `chat_result_ready` event carries no helper kind, and the client will not infer one from the title because a real chat may share that title. The PWA suppresses its own toast only by correlating the event with an authenticated chat record whose `helper.kind` is `memory_pass`; adding the equivalent authenticated lookup here, or a helper kind on the event, is the unresolved work. Until one exists, no title heuristic is used and no robust suppression is claimed.
- The opt-in is one boolean in the app's UserDefaults. It is not a cookie, credential, origin allowlist, or launch target. It is re-validated against the OS on launch without prompting: a reset or denied permission disables the row until the user opts in again. A permission change made in System Settings is noticed when the menu opens (or the next launch), not immediately.
- A bare `swift build` executable is not an app bundle, so it reports **Notifications unavailable — bare executable; use Ciaobot.app** rather than calling UserNotifications. The availability check proves only that a bundle identifier and `.app` wrapper exist; it cannot prove code signing. An unsigned or improperly provisioned bundle can therefore reach the OS boundary and fail there, which is reported as a technical registration failure with the exact message and an explicit "cannot tell whether this build is unsigned" tooltip. For manual notification checks use the ad-hoc signed, sealed `Ciaobot.app` from `scripts/package-app.sh` (the `Ciaobot.app` inside its output directory), not the unsigned `.build/Ciaobot.app` that `scripts/build-app.sh` leaves behind.
- The `/ws/events` consumer is verified against an isolated loopback fixture, not the operator's running server. Its payload handling is deliberately limited to `snapshot`, `chat_streaming_started`, `chat_streaming_done`, and `chat_result_ready`; other events are ignored. A future server change to the snapshot or result shape fails the socket closed and retries rather than guessing.
- The server's `attention_count` is treated as advisory. If it is missing, wrongly typed, negative, or incompatible with the returned rows, the valid rows are still shown and the status-bar badge/tooltip number is omitted. A structurally malformed JSON body still fails closed with **Chat list unavailable**. The badge is never derived by counting the returned rows or adding working chats. It is the endpoint's unread-plus-`needs_input` count, not every status Home can display: failed turns, board tasks waiting on the owner, and stopped memory passes are not in this payload, so the client does not claim the number covers them. If the returned page has no flagged row but the count is still positive, the menu says "N chats need attention on the server" instead of "No chats need attention".
- The tray's needs-you tier is the safe subset the endpoint exposes: `needs_input` (a persisted question or Approve/Deny card). Home also files a failed last turn, a board task waiting on the owner, and a memory pass that stopped as needs-you, but `/api/menubar-chats` sends none of those fields. The tray does not infer them from titles or from the event stream, so those variants appear only through their `unread`/`needs_input` facts until the contract grows an explicit field. `last_activity_at` is the only timestamp in the payload; Home falls back to `created_at`, which the endpoint does not send, so a chat with no activity time gets no relative label.
- The event snapshot's `active_streams` is the working source. A chat kept busy only by a background subagent or a shell (the web store's `background_agents` and running-subagent poll) is not counted by this client: those fields are not in the event subset above, and the tray will not guess working from a title or an unrelated event. Extending the decoder and tests is the required follow-up.
- The working feed is a second authenticated `/ws/events` subscription alongside the notification socket. Both are closed when the app quits; the tray feed retries with a bounded backoff while connected. It is verified against injected transports and isolated fixtures, not the operator's running server. The client does not request notification permission from this path and does not treat a working row as a banner.
- The tray still requests the endpoint's 12-row page. The server floats unread and needs-input rows to the front, but it does not know which chats are working, so a working-only chat outside that page is not displayed even though the event snapshot may list it. The tooltip's working count is derived only from the listed rows, not from every active stream id. Raising the page size or adding a server-side working field would close this gap; neither is changed here.
- The `/ws/events` client has no application-level heartbeat. A half-open network path can leave a working row until URLSession reports the socket closed and the bounded reconnect supplies a fresh snapshot. The notification socket has the same transport-level boundary; this slice does not add a ping that the server does not expect.
- Chat row selection accepts only one URL-safe path segment (`A-Z`, `a-z`, `0-9`, `-`, `_`, up to 200 bytes) and opens `/chat/<id>` with a full same-origin navigation. An id outside that set is shown disabled rather than percent-decoded or interpreted as a path. This keeps traversal, query, fragment, and control-character tricks out of native navigation; a future server that uses other characters in chat ids would need an explicit, tested encoding rule. If the main web view is not attached, one selection is queued and loaded when a view for the same origin attaches; if no matching view ever attaches, no navigation is attempted. If the selection cannot be accepted (for example after a disconnect race), an alert says so instead of silently doing nothing.
- The login-item integration is verified with injected state and failure tests, not by registering the operator's Mac. `SMAppService.mainApp` is also subject to the local app's unsigned, unnotarized build: macOS can refuse registration or require approval in System Settings > General > Login Items, and the row reports exactly that state. A real approval, a real next-login launch, and the appearance of the row after a System Settings change remain manual checks. No launch agent, helper, or privileged installer is created.
- **Hide Dock Icon** changes the app's activation policy and is unit-tested through an injected policy surface and an injected main-window-state check. It hides the Dock only while the main window is closed; an open window stays regular. The real Dock tile disappearing, the menu-bar icon remaining visible in both policies, and the main-window close observer reapplying `.accessory` are not GUI-automated. Closing the only window does not quit the app, so the tray remains the way back in.
- **Change Connected Host…** reuses the existing connection-screen flow and returns **Keep me signed in** to its default instead of carrying the previous choice to the new host. Its unit test proves that the local request is posted only after presentation succeeds, and that a failed presentation reports a visible error instead of dropping the change. A full host switch against a live installation remains manual.
- When the main SwiftUI window cannot be found, the presenter restores the saved Dock policy, activates the app, and shows an explicit alert rather than creating an `NSWindow` outside SwiftUI's ownership or silently doing nothing. The real alert and the macOS reopen/Dock-reopen path remain manual GUI checks.
- Automatic updates exist only in a release build that embeds the public feed and EdDSA key. The updater is unit-tested with a Sparkle double, so no test starts an updater or contacts the feed; a real check, download, install and relaunch on this Mac remains a manual check with a notarized release build. Feed signing (`SURequireSignedFeed`) is off for this first release, so a compromised feed could withhold or delay updates (it cannot install an archive that fails the EdDSA signature and notarization checks); turning feed signing on is the recorded follow-up, together with key rotation and delta updates. Installing the first updater-enabled build over 0.1.1 is manual because that build has no updater.
- The fixed Settings URLs are unit-tested as exact app-owned strings, but whether System Settings highlights the intended pane on every supported macOS release is a manual check. The app never uses a page-provided URL for this action.
- Real-server GUI testing, and the full quit/relaunch flow that reuses a saved session, remain manual checks. No automated test proves that a cookie written to a named store survives an actual process relaunch; WebKit's on-disk flush is not observable from the test harness, so persistence across relaunch is implemented but not yet verified end to end. Automated tests use isolated fixtures only and never contact a live server.
- The menu-bar icon’s rendered tint, the rendered attention number beside the face, the real click path through **Open Ciaobot** after closing the window, the chat-row click path, and the Dock-reopen path are covered by unit tests for their presenter and item state, but not by GUI automation. Verifying them by hand means launching this build, closing its window, and using the menu-bar item; the automated GUI launch test deliberately does not drive the operator’s running app.
- The app icon’s transparency and macOS proportions are checked from the PNG and `.icns` bytes. That does not prove a live Dock tile redraws after an in-place replacement: a running copy and Finder’s icon cache can keep showing the old square until the app is relaunched (or the bundle is rebuilt and the cache refreshed). This slice never replaces the operator’s running app, so that visual check remains manual.
- The scrollbar theme relies on the page's used `color-scheme`: the client sets it from the `theme-light` class, and WebKit paints the native (legacy) scroller from it. The installed page has no `color-scheme` of its own, and the injected `scrollbar-color` fallback is inert because Safari does not implement that property, so a future engine that overrides `color-scheme` per element, or a system switched to overlay scrollers, can change the result. The install-card rule is client-injected CSS matched to the page's setup-card class and the `/settings#install-app` link, so a renamed card silently stops being hidden instead of hiding something else. The script text and the theme/selector contract are unit-tested without a GUI; the rendered scroller colour and the hidden card are only checked by a real-WebKit fixture, which this change did not run. Whether the native scroller repaints in the operator's installed build remains a manual check.

## Prior implementation

The retired Tauri desktop app in the `ciaobot` repository at commit `20d2c23f^`, `desktop/src-tauri/src/lib.rs`, informed the window and navigation safety boundaries. Its server ownership, installer, and update behavior are not included here. In particular, its `is_external_link`, `same_origin`, `is_trusted_main_navigation`, and `on_new_window` handling were reviewed; this client keeps the origin restriction and external-link allowlist, and replaces blanket new-window refusal with same-origin child windows, OAuth placeholder decision paths that never load external content, and user-mediated downloads.
